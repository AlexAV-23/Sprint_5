# Sprint_5

## Проект автоматизации тестирования (UI-автотесты) для учебного сервиса «Доска»

1. Основа для написания автотестов — фреймворк **pytest** и библиотека **Selenium**.
2. Для создания виртуального окружения и управления зависимостями использовался менеджер пакетов — **uv**. Конфигурационный файл проекта — **pyproject.toml**. Установить зависимости — ***uv sync --dev***.
3. Команда для запуска — **uv run pytest**.
4. Тесты запускаются в **Google Chrome**.

## Описание структуры проекта

- В **корневой** директории:  
*conftest.py* — все фикстуры в одном файле.  
*constants.py* — используемые в проекте константы.  
*locators.py* — локаторы, используемые в тестах проекта.  
*.gitignore*  
*pyproject.toml* — конфигурационный файл проекта.  
*README.md* — описание проекта.  
- В директории **tests** все тесты.  
Тесты на одну функциональность в одном файле:  
*test_user_registration.py* — тесты на функциональность «Регистрация пользователя».  
*test_user_login_logout.py* — тесты на функциональность «Login пользователя»/«Logout пользователя».  
*test_creating_ad.py* — тесты на функциональность «Создание объявления».
- В директории **drivers** драйвер WebDriver для Яндекс Браузера

## Описание тестов проекта

### test_user_registration.py:

#### class TestUserRegistration:

- ***def test_user_registration_success(self, driver, mail_generation):***<br> позитивный тест регистрации: пользователь вводит корректные email и пароль, нажимает «Создать аккаунт». Тест ожидает: произошёл переход на главную страницу, в правом верхнем углу около кнопки «Разместить объявление» отображается блок аватара пользователя с дефолтной иконкой (фото при первичной регистрации не загружено — вместо него заглушка) и имя User. Если этого не происходит — тест падает, сигнализируя о дефекте функциональности.

- ***def test_user_registration_with_incorrect_email_shows_error(self, driver, wrong_mail_generation, field_name, wrapper_locator):***<br> негативный тест регистрации: пользователь вводит email, не соответствующий маске `*******@*******.***`, и нажимает «Создать аккаунт». Тест ожидает: поля Email, «Пароль», «Повторите пароль» выделены красным, под полем Email отображается сообщение «Ошибка». Если этого не происходит — тест падает, сигнализируя о дефекте валидации формы.

- ***def test_user_registration_of_existing_user_shows_error(self, driver, registered_user, field_name, wrapper_locator):***<br> негативный тест регистрации: пользователь заполняет форму данными уже существующего в системе пользователя (email генерируется фикстурой registered_user) и нажимает «Создать аккаунт». Тест ожидает: поля Email, «Пароль», «Повторите пароль» выделены красным, под полем Email отображается сообщение «Ошибка». Если этого не происходит — тест падает, сигнализируя об отсутствии защиты от дублирования аккаунтов.

## Описание хелперов

- ***def open_login_form(driver):***<br> хелпер для открытия формы входа: переходит на главную страницу (BASE_URL) и нажимает кнопку «Вход и регистрация». Ожидаемый результат: форма входа доступна для взаимодействия (локатор кнопки подтверждён, клик выполнен). Если элемент не найден или некликабелен в течение TIMEOUT — хелпер выбросит исключение, тест перейдёт в статус ERROR, сигнализируя о дефекте навигации или верстки стартовой страницы.

- ***def login(driver, email, password):***<br> хелпер авторизации: заполняет поля «Email» и «Пароль» корректными данными и нажимает «Войти». Ожидаемый результат: успешная авторизация — появляется кнопка «Выйти» (EXIT_BUTTON), что подтверждает вход в сессию. Если элементы формы или кнопка выхода не находятся либо не становятся видимыми/кликабельными — хелпер выбрасывает исключение, тест падает (ERROR), сигнализируя о дефекте формы входа или логики авторизации.

- ***def open_registration_form(driver):***<br> хелпер открытия формы регистрации: переходит на главную страницу, нажимает «Вход и регистрация», затем — кнопку «Нет аккаунта». Ожидаемый результат: открыта форма регистрации, кнопка «Нет аккаунта» была кликабельной и обработана. Если цепочка переходов прерывается (кнопка не найдена/некликабельна) — хелпер выбрасывает исключение, тест переходит в статус ERROR, указывая на дефект навигации к форме регистрации.

- ***def register(driver, email, password):***<br> хелпер регистрации пользователя: заполняет поля «Email», «Пароль», «Повторите пароль» (пароль дублируется в поле повтора) и нажимает «Создать аккаунт». Ожидаемый результат: форма отправлена, инициирован процесс регистрации (дальнейшие проверки успеха/ошибки выполняются в самом тесте). Если поля не найдены, не становятся видимыми или кнопка не кликабельна — хелпер выбрасывает исключение, тест падает (ERROR), сигнализируя о дефекте формы регистрации или её элементов.

## Описание фикстур

- ***@pytest.fixture def driver():***<br> фикстура управления браузером: перед тестом (setup) создаёт экземпляр Chrome с окном 1920×1080 в headless-режиме и передаёт его в тест; после завершения теста (teardown) закрывает браузер через driver.quit(), освобождая ресурсы независимо от результата теста. Всё, что выполняется до yield — подготовка окружения, после — очистка. Если браузер не запустился (нет драйвера, занят порт) — тест переходит в статус ERROR ещё до выполнения шагов, сигнализируя о проблеме инфраструктуры, а не о дефекте тестируемого приложения.

- ***@pytest.fixture def mail_generation():<br>*** фикстура генерации тестовых данных: возвращает случайный email вида uid_<10 символов>@yandex.ru. Случайный суффикс на основе uuid4 гарантирует уникальность email между прогонами — повторные запуски не упираются в ошибку «пользователь уже существует». Сбой здесь практически исключён: если тест не получил строку, это ошибка самого кода фикстуры, а не приложения.

- ***@pytest.fixture def wrong_mail_generation():<br>*** фикстура генерации заведомо некорректных данных: возвращает email без доменной зоны верхнего уровня (uid_<10 символов>@yandex — без .ru). Используется в негативном тесте для проверки валидации маски `*******@*******.***`. Ожидаемое поведение системы: такая строка должна быть отклонена; если система принимает её — это дефект валидации, который тест зафиксирует ассертом.

- ***@pytest.fixture def registered_user(mail_generation):<br>*** фикстура предусловия (precondition): создаёт пользователя напрямую через API-запрос POST /api/signup — без прохождения UI-сценария регистрации. После ответа фикстура проверяет код 201 ассертом с диагностическим сообщением (код и тело ответа). Если precondition не выполнен (сервер недоступен, эндпоинт изменился, регистрация не сработала) — тест падает ещё до выполнения UI-шагов со статусом FAILED, и сообщение ассерта сразу показывает, что проблема не в интерфейсе, а в предусловии. Возвращает email созданного пользователя, который тесты используют для авторизации.
